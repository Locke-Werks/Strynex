## 1. Motivation

Appendix A.3 of the base specification assigns `MERGE = 6` in `IntentCode`. No
section of v0.2 says what a participant does on receiving it.

The result is that `MERGE` is a broadcast announcement with no acceptance, no
ordering, and no commitment. A vehicle can say it intends to merge. Nothing lets
a second vehicle say it will make room, and nothing lets the first one know
whether room exists. Two conformant implementations exchanging `MERGE` are in
exactly the position two unequipped vehicles are in, which is a race resolved by
whoever is more assertive.

Base 12.1 shows the shape the answer should take. The C-ACC Group Protocol
already establishes the pattern for a multi-party commitment carried over
`Intent`: proposal, bounded confirmation window, explicit state, driver
authorization, and dissolution on timeout or breach. This profile applies that
pattern to a merge, which is the shorter-lived and more common case.

## 2. Applicability

A merge negotiation involves exactly two participants: one **merging** vehicle
seeking to enter a lane, and one **yielding** vehicle already in that lane and
positioned to open a gap.

The profile applies to lane drops, on-ramp entries, and lane closures where a
MAP or the merging vehicle's own perception establishes the target lane. It does
not apply to lane changes of convenience, which are covered by the base
`LANE_CHANGE_LEFT` and `LANE_CHANGE_RIGHT` codes and need no negotiation.

A negotiation is strictly pairwise. Multi-vehicle zipper ordering emerges from
adjacent pairwise negotiations and is not coordinated centrally. That is a
deliberate limitation: a central coordinator would need authority this profile
is forbidden by EP-0000 section 6 to create.

## 3. Code points

### 3.1 IntentCode

| Value | Name | Transmitted by | Meaning |
| --- | --- | --- | --- |
| 64 | `MERGE_REQUEST` | Merging | I intend to enter your lane ahead of you. |
| 65 | `MERGE_YIELD` | Yielding | I will open a gap. Non-binding, see section 5.3. |
| 66 | `MERGE_REFUSE` | Yielding | I will not open a gap. |
| 67 | `MERGE_COMMIT` | Merging | I am executing the lane entry now. |
| 68 | `MERGE_COMPLETE` | Merging | Entry complete. Negotiation closed. |
| 69 | `MERGE_ABORT` | Either | Negotiation cancelled. |
| 70 to 71 | Reserved | | Reserved to this profile. MUST be treated as `INTENT_UNKNOWN`. |

The base `MERGE = 6` code is unchanged and retains its v0.2 meaning: an
unaddressed announcement of merge intent. A participant implementing this
profile SHOULD continue to transmit `MERGE = 6` alongside the negotiation, so
that peers not implementing EP-0002 still receive the announcement they expect.

### 3.2 ExtensionBlock payload

```protobuf
// ExtensionBlock.profile_id = 0x0002, profile_version = 1
message MergeNegotiation {
  bytes  negotiation_id = 1;  // 8 bytes, generated by the merging vehicle
  bytes  peer_cert_id   = 2;  // 8 bytes, the addressed peer's current cert_id
  uint32 epoch          = 3;  // monotonic within a negotiation_id
  uint32 gap_request_cm = 4;  // longitudinal gap sought, MERGE_REQUEST only
  uint32 valid_for_ms   = 5;  // sender's commitment window for this message
  RefuseReason refuse_reason = 6;  // MERGE_REFUSE only
}

enum RefuseReason {
  REFUSE_UNSPECIFIED   = 0;
  REFUSE_NO_ROOM       = 1;  // yielding vehicle is itself boxed in
  REFUSE_UNSAFE        = 2;  // opening the gap would violate its own safety envelope
  REFUSE_NOT_AUTHORIZED = 3; // driver has not authorized cooperative gap changes
  REFUSE_WRONG_PEER    = 4;  // addressed vehicle is not in the target lane
}
```

`negotiation_id` is generated by the merging vehicle and MUST NOT be reused. It
is not an identifier of a vehicle and does not survive the negotiation.

`peer_cert_id` addresses the negotiation to one peer, matching the pattern base
12.1.2 uses for `PLATOON_FORM` addressed "to a specific peer (by pseudonym cert
ID)". A negotiation MUST be abandoned if the addressed peer's `cert_id` rotates
mid-negotiation; the merging vehicle re-issues against the new `cert_id` with a
fresh `negotiation_id`.

## 4. State machine

Held independently by each participant. States are local; there is no shared
state and no consensus requirement.

```text
                 +--------+
   ------------->|  IDLE  |<---------------------------+
                 +--------+                            |
                      |                                |
              MERGE_REQUEST sent                       |
                      v                                |
                +-----------+   MERGE_REFUSE           |
                | REQUESTED |------------------------->|
                +-----------+   or request timeout      |
                      |                                |
              MERGE_YIELD received                     |
                      v                                |
                +-----------+   yield lapsed,          |
                | ACCEPTED  |---- gap not verified, --->|
                +-----------+   or abort                |
                      |                                |
    MERGE_COMMIT sent, gap verified locally            |
                      v                                |
                +-----------+                          |
                | COMMITTED |---- abort --------------->|
                +-----------+                          |
                      |                                |
              entry complete                           |
                      v                                |
                +-----------+                          |
                | COMPLETE  |--------------------------+
                +-----------+
```

### 4.1 Timing

| Transition | Bound | On expiry |
| --- | --- | --- |
| `MERGE_REQUEST` to first response | 1000 ms | Merging vehicle returns to IDLE and merges conventionally. |
| REQUESTED to ACCEPTED, retransmission interval | 200 ms, at most 5 attempts | As above. |
| ACCEPTED to `MERGE_COMMIT` | 3000 ms | Merging vehicle transmits `MERGE_ABORT` and returns to IDLE. |
| COMMITTED to `MERGE_COMPLETE` | 5000 ms | Both return to IDLE. Yielding vehicle restores its production gap. |
| Yielding vehicle gap hold, after `MERGE_YIELD` | `valid_for_ms`, not exceeding 4000 ms | Gap restored to production setting without further signalling. |

The 4000 ms ceiling on a yield commitment is deliberate. A vehicle that has
promised a gap and is waiting is a vehicle behaving unlike its neighbours, and
the longer it waits the more it becomes the hazard rather than the mitigation.

## 5. Behavior

### 5.1 Merging vehicle

On selecting a target lane and a target peer:

1. Generate `negotiation_id`. Transmit `MERGE_REQUEST` addressed to the peer,
   with `gap_request_cm` set to the longitudinal gap needed, which MUST NOT be
   less than the gap the vehicle's own ACC would require at current closing
   speed.
2. On `MERGE_YIELD`, enter ACCEPTED. **Do not merge yet.**
3. Verify the gap using local sensors, per section 5.3. If and only if the gap is
   verified locally, transmit `MERGE_COMMIT` and execute.
4. On completion, transmit `MERGE_COMPLETE`.
5. On `MERGE_REFUSE`, on timeout, or on failure to verify, return to IDLE and
   merge conventionally. A refused merge is not a fault and MUST NOT be retried
   against the same peer within the same negotiation.

### 5.2 Yielding vehicle

On receiving `MERGE_REQUEST` addressed to its current `cert_id`:

1. Determine whether the gap can be opened within its own safety envelope,
   including the gap-target floors of base 12.1.6 if it is in a C-ACC Group.
2. If yes, and if driver authorization permits (section 6), transmit
   `MERGE_YIELD` with `valid_for_ms`, and open the gap.
3. If no, transmit `MERGE_REFUSE` with a reason. Refusal is a normal outcome and
   carries no trust consequence for either party.
4. Restore the production gap on `MERGE_COMPLETE`, on `MERGE_ABORT`, or on
   expiry of `valid_for_ms`.

A yielding vehicle MUST NOT open a gap by braking harder than 2.0 m/s^2. Where a
larger reduction would be needed, it refuses with `REFUSE_UNSAFE`. A cooperative
merge that requires hard braking from the yielding vehicle has moved the hazard
rather than removed it.

### 5.3 The yield is not a guarantee

This is the central safety rule of the profile and it is not negotiable.

`MERGE_YIELD` is a statement of intent by a peer. It is **not** evidence that a
gap exists. A merging vehicle MUST verify the gap against its own sensors before
transmitting `MERGE_COMMIT`, and MUST NOT execute a lane entry on the strength of
a received `MERGE_YIELD` alone.

This follows directly from base 11.2, which already states that "A cooperative
track with no local corroboration ... MUST NOT be used as sole input to
automated longitudinal or lateral control." A merge is lateral control. The rule
is restated here because this is the exact place an implementer is most tempted
to break it, and because breaking it converts a spoofed `MERGE_YIELD` into a
collision primitive available to anyone holding one valid enrollment.

Where the merging vehicle's own sensors cannot see the gap, for example a short
trailer-obscured gap on the far side of a heavy vehicle, the correct behavior is
to abort and merge conventionally. It is not to trust the peer.

## 6. Driver authorization

Base 12.1.3 requires explicit driver authorization before a vehicle joins a
C-ACC Group, and requires that authorization be revocable at any instant.

A merge negotiation is shorter-lived and lower-consequence than group
membership, and per-negotiation authorization would produce a prompt every few
seconds in dense traffic, which is worse than useless.

Therefore:

- A vehicle MUST NOT transmit `MERGE_YIELD`, or modulate its gap in response to
  a request, unless cooperative gap modulation is enabled by a standing driver
  setting. The setting MUST be revocable at any instant through the vehicle's
  HMI, matching base 12.1.3.
- Revocation takes effect immediately: any held gap is restored and any
  in-flight negotiation is aborted.
- A vehicle whose setting is off transmits `MERGE_REFUSE` with
  `REFUSE_NOT_AUTHORIZED`. It does not stay silent, because silence is
  indistinguishable from an unequipped vehicle and costs the merging vehicle a
  full 1000 ms timeout.
- Execution of the lane entry itself remains under whatever authority the
  vehicle's existing lane-change function requires. This profile grants none.

The profile satisfies the prohibitions of EP-0000 section 6. In particular it
creates no control path around base 13.1: `MERGE_COMMIT` is an announcement that
the vehicle's own lane-change function is executing, not a command to it.

## 8. Safe-ignore statement

Required by EP-0000 section 7.1. The CRITICAL flag is **never** set by this
profile.

A receiver that discards all EP-0002 extension content maps codes 64 to 71 to
`INTENT_UNKNOWN` and does nothing. From the merging vehicle's side this is
indistinguishable from a peer that did not respond: the 1000 ms timeout expires
and it merges conventionally, which is what it would have done in the absence of
this profile.

The asymmetry is worth stating: **the profile degrades to the status quo, never
to something worse.** No participant is ever left worse off by a peer that does
not implement it, and no participant can be made to wait longer than 1000 ms to
discover that.

## 9. Security and privacy analysis

**Against base 10.1.** `negotiation_id` is single-use and generated per
negotiation. `peer_cert_id` is a pseudonym already on the wire. Neither is a
persistent identifier and neither survives certificate rotation. Section 3.2
requires abandonment on peer rotation specifically so that a negotiation cannot
be used to link a pseudonym across an epoch boundary.

**Retention.** `Intent` retention is capped at 30 seconds by base 10.3, and
extension content inherits its carrying class. A completed negotiation has no
residual state.

**Adversarial cases.**

| Attack | Effect | Mitigation |
| --- | --- | --- |
| Spoofed `MERGE_YIELD` from a vehicle that will not yield | Merging vehicle attempts entry into an occupied gap | Section 5.3. Local verification is mandatory before commit. This is why the rule exists. |
| Spoofed `MERGE_REFUSE` impersonating a cooperative peer | Merging vehicle falls back to conventional merging | Denial of a courtesy, not of safety. Bounded by the fact that conventional merging is the baseline. |
| `MERGE_REQUEST` flooding | Yielding vehicles repeatedly open gaps, degrading traffic flow | Base 8.2 caps `Intent` at 10 Hz. Section 4.1 caps a yield at 4000 ms. A sender whose requests never reach `MERGE_COMMIT` exhibits internal inconsistency under base 9.3 and is de-rated. |
| Targeted repeated requests against one victim | Victim held at a widened gap indefinitely | The 4000 ms yield ceiling and automatic restoration bound the hold. Consensus deviation across victims produces misbehavior reports. |
| Negotiation with a peer that is not in the target lane | Wasted negotiation, no safety effect | `REFUSE_WRONG_PEER`. The addressed peer knows its own lane; the requester may not. |

**Residual risk.** An adversary can consume a victim's cooperative gap capacity
and can deny courtesy merges. It cannot induce a collision, because section 5.3
requires local verification before any lateral movement. That bound is the
design intent and any future revision that weakens section 5.3 invalidates this
analysis.

## 10. Conformance

| Category | Assertion |
| --- | --- |
| Wire format | `MergeNegotiation` round-trips bit-identically inside an `ExtensionBlock` inside an `Intent`. |
| Wire format | An `Intent` carrying code 70 or 71 decodes with `code` mapped to `INTENT_UNKNOWN` and does not error. |
| Timing | `MERGE_REQUEST` retransmits at 200 ms, at most 5 times, then returns to IDLE. |
| Timing | A yielding vehicle restores its production gap within one control cycle of `valid_for_ms` expiry, with no further messages exchanged. |
| Behavioral | Every state transition in section 4 occurs on its stated trigger and on no other. |
| Behavioral | `MERGE_COMMIT` is never transmitted without prior local gap verification. **This assertion is mandatory and a failure is disqualifying.** |
| Behavioral | Peer `cert_id` rotation mid-negotiation aborts the negotiation. |
| Behavioral | A vehicle with cooperative gap modulation disabled transmits `MERGE_REFUSE` with `REFUSE_NOT_AUTHORIZED` rather than remaining silent. |
| Behavioral | A vehicle in a C-ACC Group refuses any request that would breach the gap floors of base 12.1.6. |
| Safety | Yielding deceleration never exceeds 2.0 m/s^2. |
| Safety | Driver revocation of the standing authorization restores the gap and aborts in-flight negotiations immediately. |
| Safety | Loss of all peer messages mid-negotiation returns both parties to IDLE without unsafe actuation. |
| Privacy | `negotiation_id` values are never reused across negotiations by the same implementation. |
| Misbehavior | A sender issuing `MERGE_REQUEST` at the rate ceiling without ever reaching `MERGE_COMMIT` is de-rated. |

The `MERGE_COMMIT` assertion is called out because it is the one whose failure
is not detectable from the wire alone. It requires the harness to place the
implementation in a state where a `MERGE_YIELD` arrives and no gap exists, and
to confirm no commit follows. The adversarial PCAP corpus needs a vector for
this.

## 11. Open questions

1. **Whether a yielding vehicle should be able to counter-offer a smaller gap**
   rather than choosing between yield and refuse. A counter-offer adds a round
   trip against a 1000 ms budget and adds a state. It also handles the common
   case where a vehicle can open some room but not the amount requested.
2. **Whether multi-vehicle zipper ordering emerges acceptably from pairwise
   negotiation** or needs explicit sequencing. Simulation would answer this and
   has not been run. Pairwise is chosen here because it needs no coordinator, not
   because it is known to be sufficient.
3. **Whether `MERGE_REQUEST` should carry the merging vehicle's own deceleration
   capability**, so a yielding vehicle can distinguish a loaded truck that
   genuinely cannot slot in behind from a passenger car that could. This is
   information a courteous human driver reads from vehicle class and this profile
   currently discards.
4. **Interaction with EP-0007 Work Zone Protection.** Base 15.3 dissolves C-ACC
   Groups on work-zone entry, and a lane closure is the most common merge
   trigger there. Whether merge negotiation should be suppressed, mandated, or
   left unchanged inside a work zone is undecided.
